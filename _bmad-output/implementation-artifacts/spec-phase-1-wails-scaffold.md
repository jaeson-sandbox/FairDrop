## Intent

**Problem:** FairDrop is an empty repo holding only a spec. Phase 1 of the spec's execution plan (§10) requires a compiling Wails v2 + React/TS foundation with native OS file-drop enabled before any networking, streaming, or server work can begin.

**Approach:** Scaffold the `react-ts` Wails template in place at the repo root, configure `options.App` for native file drop and a standard OS window frame, declare the three `internal/` package contracts from spec §9 as compile-only interfaces, wire Tailwind v4, and prove the foundation by building a binary that receives real dropped absolute paths.

## Boundaries & Constraints

**Always:**
- Name everything **FairDrop**: Go module `fairdrop`, `outputfilename` `fairdrop`, window title `FairDrop`, mDNS service reserved as `_fairdrop._tcp`. The spec's "DeadDrop" is a stale working title.
- Scaffold **in place** at the repo root — never a nested `fairdrop/` subdirectory. Preserve existing `docs/`, `_bmad/`, `_bmad-output/`, `.git/`, `.gitignore`, `README.md`.
- Use `DragAndDrop: &options.DragAndDrop{EnableFileDrop: true}`. The spec's top-level `EnableFileDrop: true` does not exist in Wails v2.
- Frontend drop uses the runtime helper `OnFileDrop(cb, useDropTarget)`; the underlying event is `wails:file-drop`. The spec's `wails_file_drop` is wrong.
- `internal/` files in this phase declare types and interfaces ONLY — no method bodies beyond what compilation requires.

**Ask First:**
- Adding any dependency beyond Wails, Tailwind, and framer-motion.
- Any change to window chrome (frameless) — decision was standard OS frame.
- Committing or branching.

**Never:**
- Do not implement Phases 2–6: no IP resolution logic, no mDNS, no HTTP server, no zip/io.Pipe streaming, no progress tracking, no StageTransfer/CancelTransfer bodies.
- Do not build the DropZone/StagedView/TransferView UI beyond the minimal path-echo needed to prove file drop works.
- Do not hand-write `frontend/wailsjs/**` — it is generated.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Single file dropped on zone | User drags `C:\x\a.txt` onto the drop zone | `OnFileDrop` fires; UI renders the absolute path `C:\x\a.txt` | N/A |
| Directory dropped on zone | User drags folder `C:\x\dir` | UI renders the absolute directory path | N/A |
| Multi-file drop | User drags 3 files at once | All 3 absolute paths render | N/A |
| Drop outside the zone | Drop on window background (not the `--wails-drop-target` element) | Callback does not fire; UI unchanged | Silently ignored; webview must not navigate to the file |
| Component unmount | React drop component unmounts | `OnFileDropOff()` runs | No duplicate listeners on remount |

## Design Notes

Tailwind v4 differs sharply from the v3 setup most references still describe — no config file, no PostCSS, one CSS import:

```ts
// frontend/vite.config.ts
import tailwindcss from '@tailwindcss/vite'
export default defineConfig({ plugins: [tailwindcss(), react()] })
```

```css
/* frontend/src/style.css */
@import "tailwindcss";
```

Wails gates drops on a CSS custom property, not a class. The zone must compute `--wails-drop-target: drop`; Wails toggles `.wails-drop-target-active` on it during dragover for styling hooks.
