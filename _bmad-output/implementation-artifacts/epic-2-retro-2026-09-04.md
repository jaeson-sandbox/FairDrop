## Findings

### A1 — The epic's own required verification never ran, and the epic never ran

`epic-2-context.md` lists among its requirements: "Verification must cover ... **a native nearby-browser
ZIP smoke test**." A repository-wide search for such a test finds nothing, and no folder has been staged,
scanned and downloaded on a real device. Epic 1 closed with an observed transfer — a real file, a phone
scanning a QR, a completed download. Epic 2 closes with none.

Everything below the HTTP boundary is well tested; what is untested is precisely the part the epic exists
to deliver — that a **browser** accepts the produced archive. The strongest evidence in hand is
`TestStreamedArchiveOpensWithASecondImplementation`, which reads the archive with the platform's own ZIP
implementation rather than `archive/zip` — genuinely useful, and still not a browser on a phone.
*Disposition: fix now — this is the epic's stated acceptance evidence.*

### A2 — The handler is never driven with a directory payload

The epic requires "Directory progress reports ... `totalKnown=false`, `totalBytes=0`, `percent=0`.
Directory responses omit `Content-Length`." Story 2.2 verifies only `Size() == (0, false)` at the payload
level: `grep ItemDirectory internal/server/*_test.go` returns nothing, and the diff touches no file under
`internal/server`. So `writeDownloadHeaders` and `newMeter` — the code that actually omits the header and
publishes the snapshot — are never exercised with the payload kind the requirement is about.

The behaviour is very likely correct: `handler.go:137` normalises an unknown size and `:247` gates the
header on `totalKnown`, both pre-existing and tested with a stub. But a requirement phrased in terms of
response headers is verified only in terms of a payload method.
*Disposition: defer — already recorded and owned by `3-2`.*

### A3 — `AGENTS.md` lost environment knowledge whose failure mode is silence

The first commit of the epic, `a7285e0` "docs: refresh project context for epic 2", rewrote `AGENTS.md`
and dropped 23 net lines. Among them:

- how to put Go and the Wails CLI on `PATH`, absent from the default environment here;
- that `wails build` must precede a standalone `npm run build` in a fresh tree, because it regenerates
  `frontend/wailsjs/`;
- that **`go test -race` needs cgo, and without it the race detector fails with "requires cgo" rather
  than reporting a clean run — so an unset `PATH` silently skips the check instead of failing it.**

The third is the dangerous one: it describes a verification that can appear to pass while doing nothing.
Checked during this retrospective — `CGO_ENABLED=1`, `gcc` resolves to the WinLibs mingw64 toolchain, and
an instrumented run takes 1.3s against 0.7s uninstrumented — so **every `-race` result claimed in this
epic was real.** The finding is not that the checks were hollow; it is that the note explaining how they
could silently become hollow is gone, and the next agent or a fresh clone has no warning.

This is the second time a regenerated artifact has quietly lost refinement in this project. The
`epic-2-context.md` recompile during Story 2.2 dropped the staged QR-first handoff line, caught only
because it was diffed against a backup before being accepted.
*Disposition: fix now — restore the dropped pitfalls.*

### A4 — Story 2.1 was implemented, reverted, and re-derived, and the history is the only record

`1c4a468` "feat: validate and stage directories" and `f5ecf02` "docs: record story 2.1 mutation evidence"
were both reverted (`7e18d20`, `e2e538f`) and replaced by `257bf49` "feat: validate and stage one
directory". The spec's change log explains *why* the design changed — global `os.Lstat` loads Windows file
IDs lazily, so a path replaced before `SameFile` could make both values describe the replacement — which
is a genuinely good record. What no artifact records is that a full implementation was discarded to get
there. A reader of `sprint-status.yaml` sees only `done`.
*Disposition: accept — the spec change log carries the technical lesson, which is the part that matters.
Recorded here so the cost is visible.*

### A5 — The same copy loop exists three times, with three different guard sets

`payload.WriteTo` (`payload.go:388`), `archive.writeArchiveFile` (`archive.go:319`) and `archive.drain`
each implement read / context-recheck / short-write / wrap. The first two carry the `maxEmptyReads` stall
guard; `drain` does not, with no stated reason. Until this epic's review round, neither stall guard had a
test at all; `archive`'s now does, and `payload`'s remains uncovered — pre-existing, and now visibly
asymmetric.
*Disposition: defer — the third loop's missing guard is recorded; consolidating the three is a refactor
Epic 3 can weigh.*

### A6 — Two guards in the epic are unreachable by construction

`source.go`'s post-walk not-a-directory fallback was pinned during this epic by
`TestInspectRefusesAPoppedAncestorThatIsNoLongerADirectory`, which is a genuine win — it had survived every
mutation in Story 2.1. But `emitFile`'s post-open `IsRegular` recheck replaced it: `verifyOpened` already
runs `rejectUnsupportedInfo` and compares identity, so the branch cannot fire, and mutation confirms
nothing catches its removal. The pattern — layered guards where only the outer one is reachable — recurs
in this package.
*Disposition: accept, recorded in `deferred-work.md` with the reasoning, so a later reviewer does not
re-derive it as a gap.*

### Seams checked and found clean

Recorded so a later retrospective does not re-derive them: exactly one production `SourcePort` and one
`PayloadPort`, with no shadow or provider-owned duplicates; no `filepath.WalkDir`, `ReadDir(-1)`,
`os.CreateTemp` or `exec.Command` anywhere in production code; the `ItemDirectory` path reaching
`IsDir` in coordinator metadata and on to the frontend's unknown-total branch, which the reducer already
required and which needed no change; and the staged→streamed handoff, where 2.1's `LogicalSize` is used
for display only and never as a wire bound, so the two stories cannot disagree about size.

## Acceptance verdict

**accepted-with-open-items.** Criteria were **declared** — the requirements inventory in
`epic-2-context.md` and each story's acceptance criteria.

What the epic set out to build is built, and built well. Directories stage through native no-follow
handles that cannot read file contents, stream as a ZIP with no temporary archive and no retained index,
and fail safely on every path the matrix names. The architecture boundaries hold under mechanical check.
Both stories carry mutation evidence, and the review round found and fixed three load-bearing guarantees
that no test had pinned — including a bounded-memory test that was dead in two successive versions and
whose repair exposed a frozen acceptance criterion no correct implementation could ever have satisfied.

It is not **accepted**, for one reason stated plainly: **the epic's own required verification never ran.**
A native nearby-browser ZIP smoke test is in the requirements list, and no folder has reached a real
device. Epic 1 earned its verdict partly by observation; Epic 2 has only tests. Two of those tests read
the archive back with a second ZIP implementation, which is real evidence — but a phone browser is what
the epic promises, and nothing has yet asked one.

It is not **rejected**: no story is unfinished, no defect is known-shipped, and the gap is unperformed
verification rather than failed verification.
