topic: Phone-to-desktop receiving: a phone browser uploads files that the desktop saves

- (direction) Owner 2026-10-10: release 1.5.0 and in parallel begin roadmap slice 4 (phone-to-desktop receiving). Spec first; Claude orchestrates, Sonnet subagents implement; main session reviews, verifies, integrates.
- (note) Roadmap row 4 contract topics: destination approval, bounds, filenames, no overwrite surprises, partial-write cleanup, honest persistence wording. Input is sparse; product decisions requested from owner before derivation.
- (decision) Owner 2026-10-10 destination: every Receive opens a folder chooser (starting at Downloads); no listener or QR until a folder is chosen. Chooser dismissal is a no-op. Destination is per-session, memory-only, never saved to settings.
- (decision) Owner 2026-10-10 collisions: each upload writes into a fresh subfolder of the chosen destination named for the receive time (e.g. 'FairDrop 2026-10-10 14.32'); existing files are never opened for write, replaced or appended. Duplicate names inside one upload get ' (1)', ' (2)' suffixes before the extension.
- (decision) Owner 2026-10-10 approval: possessing the one-time capability URL after the sender chose a destination is the approval; no per-upload desktop Accept step. Phone page stays a script-free native HTML form.
- (decision) Owner 2026-10-10 limits: no file-count cap (many small files are legitimate). Upload is refused before writing unless its declared size fits on the destination volume with at least 3 GB (3 * 1024^3 bytes) still free afterwards; the reserve keeps the computer usable. Bytes beyond the declared size abort the upload.
- (decision) Owner 2026-10-10 partial failure: keep every file whose write completed; remove only the file being written when the upload fails. Desktop reports an incomplete upload with the exact count saved; never reports a failed upload as complete.
- (decision) Owner 2026-10-10: received outcome offers 'Show in Folder', opening the upload subfolder in Finder/File Explorer.
- (decision) Owner 2026-10-10: received files carry OS download marking (macOS com.apple.quarantine, Windows Mark of the Web Zone.Identifier) and are never created executable.
- (capability) CAP-1: A desktop user can open a receive session into a folder they choose and show a one-time QR/link. Success: chooser precedes any listener; dismissal no-op; session admitted only from IDLE through the existing coordinator lifecycle; Cancel before upload writes nothing.
- (capability) CAP-2: One phone browser can pick files on a script-free page and upload them once to the desktop. Success: first valid POST claims; files stream to disk with bounded memory into a fresh time-named subfolder; duplicates/unsafe names are renamed not refused; result page and desktop state exactly how many files were saved.
- (capability) CAP-3: The desktop user can follow and finish a receive honestly. Success: progress against declared size; Cancel/failure keeps completed files and removes the partial one; outcome states saved count and completeness; Show in Folder opens the subfolder; received files carry OS download marking and are never executable.
- (constraint) Code-grounded: internal/server readTimeout (20s) bounds the whole request read, which would cut every upload. Upload bodies need a progress-based inactivity bound instead; header timeout, MaxHeaderBytes and download behaviour stay unchanged.
- (constraint) Never buffer uploads in memory or OS temp storage (no ParseMultipartForm/ReadForm); stream each multipart file part to its destination file with bounded buffers. Missing Content-Length is refused before writing.
- (constraint) Writes are confined to one newly created subfolder of the chosen destination: exclusive creation of the subfolder and every file, no link following, temp name then flush+close then no-replace rename. A file counts as saved only after rename succeeds.
- (constraint) Persistence wording changes: FairDrop still stores no settings, history, logs or staged copies, but a receive session writes the received files into the chosen folder. Destination path never reaches HTTP, mDNS, diagnostics or the phone.
- (assumption) Space refusal (declared size would leave < 3 GB free) does not consume the session: phone sees a fixed too-large page, desktop stays waiting and is told an upload was refused for space.
- (assumption) OS download marking is best-effort: where the filesystem cannot hold it (e.g. FAT/exFAT), the file is kept and the outcome warns that marking was not applied.
- (assumption) One upload per session and one uploader, matching send semantics; receive reuses the existing capability token, QR, beacon, server lifecycle, bounded teardown and 404/423 disguise rules. Upload page is files-only (no folder picking).
- (assumption) Subfolder name 'FairDrop YYYY-MM-DD HH.MM' in local time with ' (n)' on collision, created at first file part, so an abandoned session leaves nothing behind.
- (note) Canonical spec-fairdrop SPEC (persist-nothing constraint, CAP-1/7 non-goals 'receiving on the desktop') must be re-derived when this slice is implemented, as done for collections.
- (event) Coherence PASS: CAP-1..3 each carry intent and testable success; constraints rule out per-upload approval, temp/in-memory staging, overwrite, whole-request read timeout and unbounded disk use; two non-goal lines; success signal demonstrable on native hardware.
- (event) Preservation PASS: all six roadmap row-4 topics (destination approval, bounds, filenames, no overwrite, partial-write cleanup, persistence wording) and all seven owner decisions of 2026-10-10 land in SPEC.md or receive-contract.md; assumptions listed; no open questions block implementation.
- (decision) Story A review (orchestrator, 2026-10-11): a receive outcome is held until the user leaves it (no 3 s auto-reset) so Show in Folder stays usable; leaving uses the existing Cancel command, which resets to IDLE. Show in Folder works only while the outcome is held.
- (decision) Story A review: desktop Cancel mid-upload yields a held cancelled outcome carrying the saved count (error code cancelled, result 'cancelled'); Cancel before any upload resets with nothing written.
- (decision) Story A review: a space refusal (413) is reported to the desktop as a non-terminal transfer-notice event (receive_too_large) while waiting; no new public error codes were added, so receive copy maps existing codes in receive context.
- (decision) Story A review: destination validation refuses a link or reparse point at any path component, matching the send-side source rule; a cloud-placeholder (e.g. OneDrive) or symlinked destination is refused as not a plain folder. Accepted limitation; Downloads is the default.
- (decision) Story A review: where the filesystem supports neither exclusive rename nor hard links (e.g. exFAT/FAT on macOS), saving fails closed and the upload reports incomplete; no check-then-rename fallback. Accepted limitation, to be stated in user docs.
