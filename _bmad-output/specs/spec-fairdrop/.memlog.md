- (direction by coach) Use rich-input direct extraction; product behavior follows the corrected FairDrop spec, while finalized architecture and binding contracts supersede older implementation guidance.
- (decision by coach) Adopt the final architecture spine, design explanation, and integration contracts as mandatory companions; fully absorb the original product spec, Phase 1 spec, and deferred findings as audit sources.
- (note by coach) Phase 1 scaffold is implemented; the remaining product work spans LAN discovery, streaming, HTTP transfer, coordinator and Wails integration, frontend UX, and release verification.
- (capability by coach) CAP-1 intent: Sender selects exactly one local regular file or directory through native drop or accessible browse controls. Success: one valid absolute path stages; zero, multiple, missing, link-like, reparse, or special-file selections fail safely without silently choosing or disclosing a path.
- (capability by coach) CAP-2 intent: Sender creates a receiver-reachable staged transfer on the local network. Success: Stage returns session metadata, direct URL, and QR only after a random-port listener is ready; eligible IPv4 selection is deterministic and mDNS failure becomes a safe warning when direct transfer remains usable.
- (capability by coach) CAP-3 intent: One receiver downloads the selected regular file through its capability URL. Success: the first exact-token GET receives the correct bytes and safe filename headers; wrong method, route, or token receives 404, and a competing valid request receives 423 only while the listener remains live.
- (capability by coach) CAP-4 intent: One receiver downloads the selected directory as a browser-compatible ZIP without a staged archive. Success: the response is a valid archive with one top-level root, bounded memory, normalized safe entry names, complete central directory, and explicit failure on unsafe or changed sources.
- (capability by coach) CAP-5 intent: Sender observes and controls a single transfer lifecycle. Success: backend-authoritative session events show staging, claim, honest wire progress, completion or safe failure; Cancel and shutdown quiesce every owned resource, and terminal UI returns to idle after three seconds.
- (capability by coach) CAP-6 intent: Sender operates FairDrop through a clear accessible desktop interface. Success: distinct Idle, Staged, Transferring, Done, and Error presentations expose QR and URL, filename and size, determinate or indeterminate progress, throughput, visible focus, keyboard equivalents, and live announcements.
- (capability by coach) CAP-7 intent: Maintainers can reproducibly verify and ship FairDrop on supported desktop platforms. Success: locked Go and npm builds, unit and integration tests, race checks on capable native CI, Wails builds, and Windows and macOS smoke tests all pass without relying on cross-compiled release claims.
- (constraint by coach) V1 permits one process, one live session, one selected root, and one receiver; only IDLE accepts Stage and multi-selection is rejected.
- (constraint by coach) Runtime product state is ephemeral: no database, settings, telemetry, persistent logs, cloud service, or payload archive is written.
- (constraint by coach) Payload memory remains O(buffer) regardless of payload size; files and ZIPs stream with prompt context cancellation and no whole-payload reads.
- (constraint by coach) V1 is trusted-LAN plain HTTP with a separate cryptographically random capability token of at least 128 bits; the token and source paths never enter mDNS, diagnostics, or unrelated errors.
- (constraint by coach) The coordinator is the sole lifecycle owner; external calls occur outside its mutex, commits are generation-checked, and every Stop is idempotent, force-closing, and quiescent on every return.
- (constraint by coach) Backend events and typed errors are authoritative and session-scoped; ordering, sequence, progress, public DTO, HTTP, and disclosure semantics are exactly those in the binding contracts companion.
- (constraint by coach) Preserve the proven Wails v2 native drop contract, standard OS chrome, application-lifetime Wails context, and single-instance restoration behavior defined by the architecture companion.
- (constraint by coach) Support spaces, Unicode, long Windows paths, and UNC paths wherever native Go APIs permit; never shell-interpolate paths and reject symlinks, reparse traversal, and non-regular files.
- (constraint by coach) Implementation must follow the final architecture spine and contracts; any evidence-driven divergence updates the spec, architecture memlog and documents, relevant phase artifact, tests, and managed agent context together.
- (direction by coach) Non-goal: multi-item staging, collision rules, and multi-root archives remain deferred until explicitly specified.
- (direction by coach) Non-goal: TLS, authenticated discovery, hostile-network security, cloud relay, and native receiver applications are outside trusted-LAN v1.
- (direction by coach) Non-goal: IPv6, interface-selection UI, resume or ranges, transfer history, persistent preferences, and multiple receivers are outside v1.
- (direction by coach) Non-goal: Linux packaging, installers, signing, notarization, auto-update, and default UPX compression are not part of the current product contract.
- (assumption by coach) Receiver uses a modern browser on the same trusted LAN and the sender permits the operating-system firewall prompt needed for inbound LAN HTTP.
- (assumption by coach) Host filesystem and native Go APIs determine support for long and UNC paths; unsupported native cases return typed errors rather than triggering path rewriting.
- (decision by coach) Success signal: on native Windows and macOS, a sender can choose one file and one directory in separate sessions, a nearby browser downloads exact file bytes and a valid ZIP, progress and cancellation remain honest, and every session returns to leak-free IDLE without persistent product data.
