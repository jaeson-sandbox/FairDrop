- (direction) Owner 2026-10-04 authorizes all six proposed additions sequentially by impact, starting with the recommended receiver landing page and Send Again; create specifications before Sol implementation. Main session orchestrates.
- (capability) CAP-1: A receiver opens the existing capability URL to inspect a safely escaped filename and file size or folder ZIP explanation without claiming or reading the source; explicit Download submits POST and only the first valid POST claims the transfer.
- (capability) CAP-2: After a successful send, sender can choose Send Again to revalidate the remembered item and generate a fresh session, token and code; memory only, cleared on dismissal, cancellation, replacement or unmount. Existing Send Another and retry remain.
- (constraint) Retain trusted-LAN HTTP, one live session/receiver/root, streaming, no payload copies or persistent product state, coordinator ownership and bounded teardown. Preserve generic wrong-token/method/route responses. Receiver HTML is self-contained, escaped, accessible, no scripts or external resources, no cache/referrer leaks.
- (decision) GET /download/{token} returns HTML while unclaimed; POST on the same exact path invokes existing claim-to-stream pipeline. HEAD and other methods remain generic 404. Concurrent GETs never reserve. Claimed valid GET/POST return 423 only while listener exists. Stopped listeners cannot serve an expired page. Generic failure statuses stay unchanged.
- (assumption) Use a native HTML POST form, with no JavaScript dependency or receiver installation. Add one deliberate tap after scanning. Existing direct-GET automation must adopt POST. Metadata reflects Stage inspection, not a promised snapshot or final compressed ZIP size.
- (decision) Implement independently reviewable slices in order: landing page, Send Again, multi-item streamed ZIP, browser-to-desktop receiving, connection recovery, text/link sharing. Later slices get detailed specs before implementation; roadmap is prioritization, not finalized protocol or scope.
- (event) Coherence PASS: two distinct capabilities with testable outcomes, bounded constraints and explicit non-goals. Preservation PASS: all six owner-selected additions retained in ordered roadmap; CAP-1 and CAP-2 specified, later detailed specs precede their implementation. Assumptions recorded; no blocking questions for CAP-1.
