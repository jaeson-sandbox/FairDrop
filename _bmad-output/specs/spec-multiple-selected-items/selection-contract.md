# Collection selection contract

## Sender interaction

Preserve immediate single-item drop and existing File/Folder browse actions. Add a secondary **Send multiple items** action in Idle which opens a selection list. A native drop of two or more paths opens the list with those paths, rather than silently selecting the first. While the list is open, native drops append. All native drops continue through Wails' drop target.

The list has **Add Files**, **Add Folder**, per-row **Remove [basename]**, **Send**, and **Cancel** controls. Add Files uses Wails OpenMultipleFilesDialog; Add Folder uses the existing single-directory chooser and can be repeated. Wails' multiple-file dialog does not select directories, so do not imply it does. Rows show basenames only, with item order and a count out of 10,000. The list scrolls within the window at large counts, and keyboard focus stays visible inside it. No drag reordering or per-item metadata lookup is needed. Input order is archive order. Empty list disables Send. One remaining item uses the ordinary single-item pipeline; two through 10,000 use the collection pipeline. Cancellation clears the list and returns focus to the entry action. Chooser dismissal is a no-op. Removing a row moves focus to a remaining adjacent Remove control or Add Files. Use the Quartz tokens, existing button treatments, explicit programmatic focus indicators, forced-colors outlines and live announcements. Do not open a listener until Send.

The list is available only when the controller may admit a fresh selection. An attempted multi-drop on a live Done/Error releases the terminal lease through the existing guarded outcome action before opening it. During staged/transferring or pending chooser/Stage/release, reject duplicate admissions safely. Cancel/unmount invalidates outstanding chooser completions. New selection list work replaces/forgets retained Send Again state. Send Again and error retry remember immutable copies of the last staged paths, never view state or persistence. Preserve existing release-failure recovery and single-flight guarantees.

## Admission and public errors

Keep StageTransfer(string) as a backwards-compatible one-item wrapper. Add StageTransfers([]string) and SelectFiles() bound commands, regenerating bindings through Wails. Zero paths and more than 10,000 fail `invalid_selection` before filesystem inspection; never trim a too-large list. 10,000 is a sanity cap against a broken or accidental selection, not a resource budget. Invalid source policy follows existing codes. Backend remains authoritative even if frontend count checks passed.

After coordinator admission, inspect each path sequentially through the existing bounded ancestor-resolution decorator. Copy caller-owned slices at admission and every immutable cross-port boundary. Reject duplicate canonical paths and canonical ancestor/descendant pairs using component-aware comparison, including case-insensitive Windows paths; do not mistake `/a/b` for an ancestor of `/a/b2`. Distinct hard links are allowed as separately named selections. Reject overlap as `invalid_selection`, not silent deduplication. Checked sum must lie in 0..9007199254740991; overflow is `path_unsupported`. No network resource acquisition or lifecycle event may precede complete validation. Cancellation between members stops admission without claiming an interrupted native OS call. Preserve the decorator's generation-scoped busy flag and bounded recovery: only one admitted resolution runs until it completes or its bound releases admission. A timed-out native call may remain blocked; do not claim it stopped or strengthen this into indefinite refusal.

## Metadata and archive layout

Represent a collection explicitly in domain/public types rather than pretending a nonexistent directory exists. Add an explicit collection discriminator/count in metadata, with strict frontend validation; preserve valid single-item DTO handling and truthful file/folder labels. For multiple items, sender and receiver show **N items**, aggregate logical size and **Downloads as ZIP**. Receipt, announcements, pending/transferring views and Send Again must recognize collections rather than calling them a folder. No absolute paths or per-root path list crosses the public metadata boundary. GET remains escaped metadata only; POST retains exactly-one-claim semantics.

Use attachment name **FairDrop.zip** and top-level directory **FairDrop/**. Member i (one-based) is `FairDrop/<ordinal>-<safe-basename>`, where the ordinal is zero-padded to max(2, digits in the item count): `01`–`16` for 16 items, `001`–`100` for 100, `0001`–`1000` for 1,000, `00001`–`10000` for 10,000. Padding keeps names distinct and in selection order when sorted; directories retain their subtree under that member, files are direct entries. For example, two `report.txt` files become `FairDrop/01-report.txt` and `FairDrop/02-report.txt`. Use existing root sanitization/fallback and enforce SafeArchiveSegment after prefixing, bounded to 200 runes and 255 UTF-8 bytes including the ordinal of any width. Truncate only on rune boundaries, trim newly exposed trailing dots/spaces and use the existing fallback when sanitation empties the basename, without removing the ordinal. Never use full source paths. Prefixes distinguish even case/Unicode-equivalent basenames without an unbounded collision index. Nested names preserve current security-refusal and portability-warning policy; this feature makes no promise of fixing existing within-folder collisions.

ZIP length is unknown before streaming: aggregate source bytes are display metadata, not Content-Length or percent denominator. Reuse existing deterministic permissions, empty-directory support, ZIP64 and finalization semantics. Do not nest per-folder ZIP files inside the collection ZIP.

## Preparation, ownership and memory

Inspect remains metadata-only. Collection preparation happens only after authorized POST and preserves per-kind revalidation: files compare staged kind/size/mtime and verify the opened descriptor identity; directories acquire the existing fresh no-follow prepared identity pin without a new content enumeration or staged size/mtime equality requirement. Prepare members lazily, one at a time, in archive order: prepare the first member before headers, so its failure is a clean pre-stream refusal, and each later member when the stream reaches it, closing it before the next is prepared. At most one top-level file descriptor and one prepared directory pin are retained at any moment, whatever the item count. A later member that fails preparation aborts the ZIP without finalization. This supersedes the earlier all-members-before-headers rule (owner decision 2026-10-11). Failure/cancellation closes everything already acquired, and reports close failures honestly. Close-before-WriteTo releases all resources; repeated Close is safe; writing twice is refused.

The existing 64 retained directory-handle budget applies as for a single folder: the one current pin plus lexical ancestors and active traversal, with three transient handles maximum. Because pins are no longer accumulated, Stage inspection reserves one future pin per directory, as the singleton path does, and the count of selected folders never consumes the budget. Retained top-level file descriptors are at most one. Walk roots serially, borrow at most one descendant reader, reuse bounded copy storage, and preserve join-before-close ownership. No independent worker per root, no total-descendant list, no whole-file reads, and no bytes written to staging storage.

Preserve all no-follow and identity checks. Each member's identity is pinned at its own preparation, not at Stage: a member changed, replaced or removed between Stage and its turn fails as `source_changed`, `path_not_found` or `path_unsupported` during the stream. A directory root replaced between its preparation and its walk is refused by the walk. If a prepared file pathname is replaced, its already verified open descriptor continues reading the original object; never read substituted content. Neither behavior promises a content snapshot. A failure in any member aborts ZIP output without successful central-directory finalization. Success follows HTTP framing completion; it does not prove the receiver saved bytes. Existing bounded teardown and unquiescent-resource reporting remain authoritative.
