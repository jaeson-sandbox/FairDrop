# FairDrop 1.7.0

FairDrop 1.7.0 adds connection recovery and short text or link sharing. It also fixes a race between a refused phone upload and a new upload claim.

- **Refresh a waiting connection.** If the nearby device cannot open a waiting send or receive page, open **Trouble connecting?**. Choose an eligible local IPv4 network or Automatic, then select **Refresh connection**. FairDrop retires the old code and makes a fresh link and QR code while keeping the selected file paths, text, or approved receive folder. It rechecks file selections before offering the fresh code. If replacement fails after retirement, the old code stays invalid; start a new session. The network list shows local addresses; it does not test whether a nearby device can reach them. An upload or download that has already claimed the session cannot be moved or resumed this way.
- **Send a short note or URL.** Choose **Send text** and enter up to 65,536 UTF-8 bytes. FairDrop changes CRLF and CR line endings to LF and refuses blank text or unsupported control characters. A receiver opening the link sees only the byte length. Pressing **Read text** claims the one-shot link and reveals the text in a selectable, read-only field for the browser or device's ordinary Copy command. URLs remain plain text; FairDrop does not open or preview them. This works without browser scripting or clipboard permission. **Send Again** and waiting **Refresh connection** offer the same bounded value with a fresh code; FairDrop keeps it only in memory until you cancel, dismiss, or replace the session. Text sharing goes from desktop to browser only.
- **Receive claims remain valid after a refusal notice.** A refused phone upload can leave the receive link waiting for another try. If a valid upload claims the link while FairDrop is reporting that refusal, it waits briefly for the notice to finish and can continue using that same link, instead of being lost to the race. The wait is bounded; cancellation or a timeout can still fail the claim. Receiving still saves completed files in the chosen folder, removes an incomplete file, never overwrites an existing file, and reports an incomplete upload honestly.

For text, **Text sent** means FairDrop wrote and finalized the complete local HTTP response. It does not prove the nearby device received, read, or copied the text. A browser or operating system may retain a revealed page or a copy; FairDrop cannot erase those copies.

Receiving still needs a plain writable folder with at least 3 GiB free after the upload. Linked folders and cloud placeholder folders are refused; on macOS, receiving to FAT or exFAT volumes fails closed. See the [receiving limits in the README](https://github.com/jaeson-sandbox/FairDrop/blob/v1.7.0/README.md).

FairDrop stores no settings, history, logs, or remembered receive folder. The only files it writes are files you choose to receive. Transfers use plain HTTP on a trusted LAN. A single-use capability link reduces blind discovery, but does not protect against an observer on that network. There is no encryption, authentication, or relay.

The Windows executable is unsigned. The macOS app has only an ad-hoc signature (`codesign --sign -`) so it can launch; it has no Developer ID signature or notarization. There is no auto-update or Linux packaging. SHA-256 sidecars let you check that downloaded assets arrived intact. A checksum proves integrity, not authenticity: the checksum and binary come from the same release pipeline. It is not a signature.
