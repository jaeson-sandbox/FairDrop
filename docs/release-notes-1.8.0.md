# FairDrop 1.8.0

FairDrop 1.8.0 adds phone-to-desktop text and link receiving. A nearby browser can submit one short note or URL, which FairDrop holds in desktop memory for inspection and an optional copy.

- **Receive text without choosing a folder.** Select **Receive text** and scan the one-time QR code. The phone opens a script-free form on the trusted local network. Enter text and press **Send text**. An invalid submission leaves the link available for correction; FairDrop does not echo the rejected text into its retry form. One complete valid submission claims the link. **Text received** means FairDrop committed the value in memory on this computer. It does not mean the phone received its acknowledgement, the text was saved to disk, or another app received it.
- **Inspect, then copy explicitly.** The desktop shows the accepted value in a selectable, read-only field until **Done**. A URL stays inert text; FairDrop does not open or fetch it. **Copy text** writes through the native OS clipboard only when selected, and FairDrop reports **Copied** only after that write succeeds. If the clipboard write fails, the text remains available for another try. There is no automatic clipboard access.
- **Bounded, one-shot receipt.** FairDrop accepts at most 131,072 raw UTF-8 bytes and 65,536 UTF-8 bytes after changing CRLF and CR line endings to LF. It preserves other accepted whitespace, including leading newlines, and refuses invalid UTF-8, blank text, unsupported controls, or text over either limit without truncating it. TAB and LF are accepted; CR is normalized to LF; other C0 controls and DEL are refused. Refreshing a waiting link issues a new code and retires the old link. A completed receipt stays on screen until **Done** and is not available for a second submission; **Done** followed by **Receive text** starts a fresh, empty session. See the [receiving instructions](https://github.com/jaeson-sandbox/FairDrop/blob/v1.8.0/README.md).

FairDrop keeps the accepted value in bounded application memory only while its current receive session is active. **Done**, cancellation, replacement, or shutdown clears FairDrop's references. This is not secure erasure of browser, Go, or operating-system memory. A phone browser may retain what was typed, and an explicit copy remains on the OS clipboard after FairDrop clears its own state.

File receiving still needs a plain writable folder and at least 3 GiB free after an upload. Linked or cloud placeholder folders are refused, and macOS FAT or exFAT destinations fail closed. See the [receiving limits](https://github.com/jaeson-sandbox/FairDrop/blob/v1.8.0/README.md).

Transfers use plain HTTP on a trusted LAN. A single-use capability link reduces blind discovery but does not protect against an observer on that network. There is no encryption, authentication, or relay. FairDrop stores no settings, history, logs, or remembered receive folder; the files you choose to receive are the only files it writes.

The Windows executable is unsigned. The macOS app has only an ad-hoc signature (`codesign --sign -`) so it can launch; it has no Developer ID signature or notarization. There is no auto-update or Linux packaging. SHA-256 sidecars let you check that downloaded assets arrived intact. A checksum proves integrity, not authenticity: the checksum and binary come from the same release pipeline. It is not a signature.
