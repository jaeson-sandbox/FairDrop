# FairDrop 1.5.0

FairDrop 1.5.0 lets you send several files and folders to one receiver as a single download.

- **Send multiple items as one ZIP.** Drop 2 to 16 files and folders on the window together, or choose **Send multiple items** and build a list with **Add Files** and **Add Folder**. A multi-item drop opens the list rather than sending the first item, and you can remove rows with **Remove** before pressing **Send**. The list shows base names only, in the order you chose. FairDrop does not open a listener until you press **Send**. Selections of more than 16 items, duplicates, and a folder together with something inside it are refused, not trimmed or merged.
- **One download for the receiver.** The preview page and the sender window show the item count and total logical size, and mark the download as a ZIP. The receiver presses **Download** and receives one streamed `FairDrop.zip`. Inside, each selected item is a numbered member under `FairDrop/`, for example `FairDrop/01-report.txt` and `FairDrop/02-report.txt`, so items with the same name stay distinct. Folders keep their contents under their member name. Absolute paths are never shown to the receiver. The total ZIP size is not known in advance, so progress does not show a percentage.
- **All or nothing.** FairDrop checks the whole selection before it starts sharing. If any item cannot be used, nothing is offered. If any item fails while the ZIP is being sent, the whole transfer fails and the receiver does not get a completed archive. **Send Again** and **Try Again** check every item again and use a fresh link and QR code. Like single items, a collection is read from the current files and folders at send time; FairDrop does not take a snapshot or keep a staged copy.
- **One file or one folder is unchanged.** Selecting a single item works as it did in 1.4.0: the receiver previews it, presses **Download**, and gets the file itself or, for a folder, a streamed ZIP of it. The 1.4.0 rule that direct clients must POST to the capability URL still applies.

FairDrop transfers to one receiver over plain HTTP on a trusted LAN. A capability URL limits blind discovery; it does not protect against an observer on that network. There is no encryption, authentication or relay. Sender-side completion does not prove the browser saved the bytes. The selection list and any remembered paths for Send Again live in memory only; there is no history, queue, resume or desktop receiving.

The Windows executable is unsigned. The macOS app is ad-hoc signed only for launch, with no Developer ID signature or notarization. There is no auto-update or Linux packaging. SHA-256 sidecars let you check that downloaded assets match the release assets. A checksum proves integrity, not authenticity: the checksum and binary come from the same release pipeline. It is not a signature.
